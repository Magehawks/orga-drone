# Secure pairing spike (#273)

Status: architecture and threat model only. This does not change pairing,
does not store a credential, and does not enable a new connection path.

## What ships today

`ControlService.enable` accepts a caller-supplied 64-hex `pairing_key`. The
process keeps only `SHA-256(key)` in memory and compares a later bearer with
`hmac.compare_digest`. `disable` and process exit drop that digest. The
editing lease is 3 seconds. A second session is refused while the lease is
live, and a fenced session cannot keep editing. Loopback Host/Origin checks
stay in `local_http.py`.

The key is not written by `enable`. It is also not generated by the app, not
protected with DPAPI, and not bound to an OS user secret. Whoever can supply
the same 64 hex digits can present the bearer until the process disables
control or exits.

## Threat model

The assistant and Orga Drone run as the same Windows user. That user can read
the process memory, the command line, files in the user profile, and a DPAPI
blob decrypted in that logon session. DPAPI and a restrictive ACL stop other
users and a copied file on another machine. They do not stop malware that is
already running as the pilot.

Out of scope for any later implementation: cloud accounts, a key in a Codex
config file, a key on the command line, a key in a log, and a key pasted into
chat.

## Preferred later design

Not implemented here. A reviewed follow-up would:

1. Let Orga Drone generate a fresh 256-bit credential per approval.
2. Show an explicit approval in the app. Closing the app or choosing
   Disconnect revokes that credential.
3. Hand the secret to the local assistant through a protected channel, not a
   command line and not a world-readable file.
4. Store any at-rest copy with Windows DPAPI and an ACL limited to the
   current user.
5. Keep the existing loopback, Origin, bearer, lease, and stale-token checks.
6. Make each connection identity revocable without disabling every future
   approval.

Same-user memory access remains a residual risk. The design reduces
accidental persistence and reuse after restart. It does not create a security
boundary between two processes of the same user.

## Recommendation

NO production pairing change in 2.4.0 until a reviewed contract accepts that
residual risk. This spike does not add DPAPI, a new route, or a stored key.
