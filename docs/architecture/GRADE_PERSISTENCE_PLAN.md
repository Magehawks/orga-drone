## Verified persistence and startup

- `config.py::Settings.db_path` currently always returns `data_dir / "orga-drone.sqlite3"`. `ORGA_DRONE_DATA_DIR` selects the directory; there is no version-aware store selector here.
- `app.py::create_app` constructs `Database(settings.db_path)` early. `Database.__init__` creates the parent and calls `_init_schema`; this executes SCHEMA and `_migrate`. A compatibility check after construction is too late to claim a read-only/minimum-reader admission gate.
- `Database.connect` owns SQLite connection/commit/rollback/close. Callers can reuse one connection in the newer transactional APIs; many old setters still open their own transactions and re-read after commit. Do not nest them inside a purported atomic grade transaction and assume a rollback will undo an earlier connection's commit.
- `studio_clips.effect_settings` already stores extensible JSON. No new column/table is demonstrated necessary for the grade envelope. Existing `app_state` can potentially store revision/activation metadata without schema changes; its key semantics and concurrency protocol require review before use.
- User media and soundtracks remain references. Application-owned LUTs are in `data_dir/luts`; imported overlay assets are in `data_dir/overlay-assets`. A database-only backup does not prove rollback preserves old looks if the newer app deletes/replaces these assets in the shared directory. Asset namespaces must be part of the fork/recovery contract. Source media, flight logs and soundtracks must not be copied into backups by this feature.
- Rescan must retain media_meta, album_items and studio_clips exactly as before. A grade read must not select a new database, normalize/save JSON, call a setter or trigger a wrapper conversion.

## Existing history: reuse and limits

`studio_history.py` already supplies a process RLock, project-keyed stacks, 50-entry session history, full clip-row snapshots and project music start. `transactional_story_edit` captures before/after inside BEGIN IMMEDIATE and publishes stacks after commit; `transactional_story_undo` has a pre-restore validation hook and publishes stacks after commit. These are the primary reusable boundaries.

Generic Story undo intentionally restores a PROJECT snapshot. A row's presence in that snapshot is not proof that the last mutation targeted that clip. `guarded_undo_values` alone is insufficient command attribution. Existing ControlService additionally compares ExternalOperation(session/project/clip/command/history revision/fingerprint), and existing two-clip tests cover that legacy integration. Reuse those checks; do not infer a new cross-target defect from the snapshot design or bypass its surrounding guard.

`redo_story` currently pops/restores the snapshot via its own connection and then updates stacks; canonical revision reassignment must occur in the SAME SQLite transaction as the restored JSON. Snapshot-restored old grade revisions would permit stale requests. Both undo and redo need a serial, reviewed extension; do not patch only the forward grade setter.

Gesture grouping currently uses a string open_group. Future canonical grouping must bind project, clip, command/gesture and mutation type, so reusing a group ID across A/B cannot coalesce distinct targets. A grade-specific undo/redo must match the top entry's recorded mutation and expected revision, never search an older entry or claim a clip was undone because its row existed in a project snapshot. Generic Story undo remains project-scoped and must refresh every affected canonical revision.

Do not create a second undo engine. Extend existing history entries with reviewed provenance and reuse its transactional snapshot machinery. A confirmed cross-target or non-atomic restore regression is a STOP condition, not a finding to fix opportunistically outside approved safety design.

## A. Store and asset selectors

Let L be the resolved configured legacy base, C=`L/grade-store-v1`, R=`L/grade-recovery-v1/<UTC timestamp>-<UUID>`. Keep `L/orga-drone.sqlite3` unchanged. Canonical DB: `C/orga-drone-grade-v1.sqlite3`. Canonical assets exist ONLY at `C/owned-assets-v1/lut-objects-v1/<sha256>.cube` and `C/owned-assets-v1/overlay-objects-v1/<sha256>.(png|jpg)`. Retain original imported asset bytes/format without re-encoding, with explicit original logical-ID binding. Recovery uses the SAME owned-assets-v1 layout beneath R; DB is `R/legacy-snapshot.sqlite3`. No canonical/recovery namespace contains legacy asset aliases named luts or overlay-assets. No symlinks, junctions or hard links connect retained payloads to a legacy asset directory or another store; copies have independent file identity.

Saved logical legacy IDs remain unchanged. Typed canonical resolvers map IDs to immutable content SHA and owned object paths: LUT catalog hashes plus reserved asset keys below, not a fabricated data_dir passed to old helpers. Create-only payload publication: same hash requires identical bytes; changed content gets a new binding, never replaces referenced bytes. Existing validation/LUT/image processing is reused; path routing is a serial #351/#352 gate without changing color math or the renderer. No automatic asset GC/pruning in this milestone. Internal managed folders are not supported user-library/source roots; explicitly registering them as source media or manually rewriting files/aliases is outside this launch/override asset-selector guarantee, not an implied protection against arbitrary same-user file operations.

Pinned old behavior is source `488afebfffaa6aad3cd8afa6aaae9981183d9627`, including lut_library.ensure_legacy_catalog/delete_lut, studio_lut/studio_overlay resolvers and local_cache.clear_regenerable_cache. For old override D, selectors are D/luts/<32hex>.cube and D/overlay-assets/<32hex>.(png|jpg). These cannot select either custom object directory; 64-hex physical names also fail old 32-hex validation. D=C, an object root, its parent, R or an ancestor may create/delete the OLD APP'S OWN directories/catalog/bait files, not protected payloads. Do not invent an overlay DELETE endpoint: exercise actual old import/resolve/clip-overlay removal/cleanup behavior.

Old cache clear recursively visits thumbs, osm-tiles, preview-stills, hsl-luts and color-wheel-luts. Therefore reject C/R/staging/protected files if ANY resolved physical ancestor is one of those components (case-folded conservatively), even if L itself was configured inside a cache. Resolve Windows final/long paths and Linux real paths, reject unexpected protected-file links/reparse points/path escapes and recheck file identity at access. No claim that a new suffix prevents an ancestor's recursive deletion. Manual same-user file replacement/alias creation remains outside the unmodified-launch guarantee; ambiguous admission fails closed.

OLD-ASSET acceptance: pinned old binary or frozen compatibility harness with exact source hashes, no new resolver monkeypatches. Seed a canonical clip with LUT AND overlay; hash DB, bindings and payloads. For D in L/C/owned-assets-v1/both object roots/R and relevant ancestors, run old startup/discovery/list/import/LUT-delete (including a seeded same-logical-ID old catalog bait), actual overlay operations and cache clear. Protected hashes/bindings stay identical and the canonical clip resolves both assets afterward. Include default/ORGA_DRONE_DATA_DIR, case/8.3 aliases, relative paths, fresh empty old DB and old missing/in-use asset errors. Test unsafe placement rejection. Runtime proof on Windows packaged and Linux is mandatory, currently NOT_RUN.

## B. Lifetime single-writer ownership (no fallback)

Own the ENTIRE canonical store, not one project/transaction. Permanent lock path is `C/store-owner-v1.lock`, acquired BEFORE any canonical Database constructor/schema initializer/writable SQLite open/asset write/activation/repair. Every supported alias resolves the SAME physical lock identity. Never unlink, rename or replace a lock to clear a stale owner. PID/time/heartbeat is diagnostic, never evidence that a lock can be stolen.

Windows: CreateFileW with GENERIC_READ|GENERIC_WRITE, share mode 0 (including no delete sharing), OPEN_ALWAYS, non-inheritable handle, held throughout ownership. Contention or inspection/permission/path failure rejects before initialization (STORE_IN_USE or STORE_ADMISSION_FAILED). Windows denies incompatible subsequent opens until the owning handle is closed; handles close on process termination. Test actual independent processes and delayed release, not just a mutex. Sources: [Microsoft CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [file handles](https://learn.microsoft.com/en-us/windows/win32/fileio/file-handles). This is a proposed use of documented semantics, not runtime evidence.

Linux: open permanent regular file O_RDWR|O_CREAT|O_CLOEXEC|O_NOFOLLOW, mode 0600; verify current uid, physical identity and link count; flock(LOCK_EX|LOCK_NB). Contention fails before initialization. flock is advisory: ALL supported canonical writers must participate; arbitrary raw SQLite/filesystem writers are not covered. Hold descriptor strongly for lifetime. Install child-fork close/invalidate handling before ownership: children close inherited descriptor WITHOUT LOCK_UN, cannot use inherited StoreLease; CLOEXEC alone does not handle fork. Helper/FFmpeg children inherit no lock or writable DB handles. Source: [Linux flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html).

Initial production filesystem scope: local NTFS on Windows, local ext4/XFS on Linux, with platform-specific proof. Reject network/UNC/SMB/NFS, FUSE/cloud-synced or unknown/unverified filesystems and unreliable identity/locking/durability; no best-effort fallback. A second-process contention probe supplements, not replaces, platform evidence. POSIX directories 0700/files 0600, current uid; Windows verified per-user owner/DACL with no other-user write and normal system/admin access. Failure to verify supported access blocks. These controls are not protection from manual same-user tampering.

The initial OwnershipLock is only the exclusive kernel handle, not write permission. After read-only admission, a writable runtime advances E and receives StoreLease containing PID, live kernel handle/descriptor, root/file identity, immutable store generation G and admitted owner_epoch E. Read-only restore inspection can hold OwnershipLock without issuing a StoreLease or changing E/source metadata. Every write-capable constructor/helper/transaction/asset path requires it; same-process DB objects/threads SHARE one lease, not a new lease per connection. Canonical Database construction without it fails before initialization. Lock order is lease -> existing history RLock -> SQLite transaction. Shutdown stops admissions, joins/cancels writers/jobs, closes all connections and flushes owned work BEFORE release. Late callbacks fail STORE_OWNERSHIP_LOST. Never release ownership between commits or leave a background writer alive afterward.

Crash/TerminateProcess/SIGKILL: kernel releases ownership after owning handles disappear; no age-based unlock. A new process must acquire that same lock, recover/validate SQLite under admission and advance E atomically before mutations. All old history stacks/queued tickets are invalid. A live process that loses/closes/mismatches its lease disables IO, re-admits with EMPTY history or stops; never resumes its old snapshot. Fork/inheritance, stalled live owner, simultaneous restart, late worker and direct-helper bypass tests are mandatory. Failure of lifetime exclusion is STOP. The project fence below is defense in depth, NOT permission to enable a multi-writer fallback.

## C. Exact durable keys and retention (existing app_state only)

Use reserved `grade.v1/` keys in existing app_state(key TEXT PRIMARY KEY,value TEXT NOT NULL). Strict versioned JSON, canonical safe integer IDs/UUIDs; no new table/column assumed. Refuse legacy sources with colliding reserved keys or ambiguous canonical content. Generic setters cannot overwrite this namespace; project row snapshots never restore it.

- `grade.v1/store`: {format:1, generation:G (UUID), owner_epoch:E, last_revision:N}. G never changes in place; E increments on each admitted owner lifetime, N is a global high-water mark. E/N are JS-safe integers; exhaustion aborts, never resets/wraps. A restored/new store has a NEW G, invalidating old tickets.
- `grade.v1/project/<pid>`: {instance:UUID, history_seq:S, present:bool}. Every successful project-snapshot content mutation advances S in the same transaction, including legacy/other clip edits, structural operations and music_start_s. Retain deletion tombstones; reused numeric project ID gets a new instance and advances the retained sequence.
- `grade.v1/clip/<pid>/<cid>`: {project_instance, instance:UUID, revision:R, present:bool}. Every changed/created/restored/deleted clip gets next N. Keep tombstones through delete/clear/project deletion; reused numeric IDs get NEW instances and R. Canonical JSON grade.revision equals R. Raw legacy JSON stays unchanged, but action snapshots expose effective_revision=R separately from pure model_revision=0. Seed identities/effective tokens during activation without wrapping or rewriting legacy JSON. Never use legacy sentinel 0 as the persistent concurrency token after wrap/Undo.
- `grade.v1/receipt/<command-UUID>`: immutable {format,G,owner_epoch,actor_scope,project/clip IDs and instances,request_sha256,mutation_id,direction,undo_of/redo_of,expected_revision,result_revision,project_seq_before/after,applied/no_op,result_code}. Hash covers canonical DOMAIN command, expected revision, actor scope, G and exact target instances; excludes transport secrets/transient ack state. Not the render digest. No bearer/session token/media bytes. Project-scoped actions list affected clip instances; never pretend a whole-project restore was one selected clip.
- `grade.v1/asset/<kind>/<logical-ID>`: immutable {content_sha256,byte_length,retained_format}. Kind selects only A's typed directory. LUT catalog and binding agree. Publish verified create-only payload BEFORE the referencing transaction. Rollback may leave an unreferenced immutable object for explicit future recovery, never a committed dangling reference; no automatic object pruning.

Retention: all accepted receipts, tombstones, counters persist for lifetime of G, including restart/deletion. NO automatic TTL, size eviction or pruning in this milestone. Receipts hold bounded metadata, not full grade/project/media blobs. A no-op gets a receipt but does NOT advance N/R/S, updated_at or history. Disk/I/O failure aborts before commit; receipt growth is an explicit cost, not solved by discarding replay protection. Recovery uses a new G while retaining the old store/recovery evidence; never reset a live store's counters.

## D. Atomic mutation and retry protocol

Merged Foundation read_grade/validate_patch remains sole parsing/pure validation. Proposed studio_grade_persistence.py owns transactional actions; studio_grade_store.py owns admission/backup/lease. #363 later consumes the SAME actions with existing authorization/selection rules. No new public endpoint. A persistent wrapper supplies UUID/actor_scope/G/project_instance/clip_instance around the unchanged Foundation command shape. Explicit legacy wrapping is its own opt-in internal action, never a read/slider side effect.

With live lease + history guard, BEGIN IMMEDIATE, bounded 5-second SQLite busy timeout. Verify DB G/E and target instances against the lease/context. After validated authorized identity, look up receipt: exact UUID+digest+target returns original HISTORICAL result, replayed=true, and separately read current_revision/current S, with NO mutation/history move. #363 must not display it as current grade. UUID reuse with different target/instance/actor/payload/expected revision is COMMAND_CONFLICT, even after deletion. A new UUID requires current effective revision or STALE_REVISION. Failed requests have no success receipt; no selection change retargets an already validated command.

Validate detached proposal and history fence, allocate tokens, update matched project/clip/instance/expected-state rows and assert row counts; update S/timestamp, capture history and prepare receipt using ONE connection. All snapshot-changing writer paths participate before first canonical write; no nested legacy setter connection commits independently. Pre-commit failure rolls back JSON/N/R/S/timestamps/receipts and leaves stacks/cursor untouched. After commit publish preallocated history transition and acknowledge durable receipt. If bookkeeping/ack fails after commit, quarantine/clear in-memory history, reload durable state under lease, return recoverable committed evidence; never claim rollback or replay a committed edit. No-op writes only its receipt, not grade/content/history/fence. No source/export/existing asset is deleted as rollback.

## E. Undo/Redo and distinct-clip cross-process fences

Extend existing history entries, not a second engine: G,E,project ID/instance,mutation/command UUID,scope clip|project,exact affected instances and existing before/after project snapshots. A per-project in-memory cursor records last accepted durable S. Every forward edit, Undo AND Redo verifies G/E/project instance and cursor==durable S INSIDE its write transaction BEFORE restore. Clip-targeted Undo/Redo also requires requested command/mutation/instance at the TOP entry; no search past another clip's edit. Another clip's intervening S invalidates restore even when A's own R is unchanged.

Healthy forward/Undo/Redo increments S once and issues fresh R for every changed/created/restored/deleted row. After commit move exactly one entry/update cursor to committed S; old entries never restore old counters. Forward edits clear Redo; group key binds G/E/project/clip instance + gesture + action. Rollback leaves stacks/cursor unchanged. Unexpected fence mismatch is HISTORY_CONFLICT and quarantines stale stacks, not automatic snapshot rebasing. Restart/re-admission starts EMPTY history; durable revisions/receipts remain. Generic project Story Undo uses the same fence and token refresh; it never restores grade.v1 metadata from a snapshot.

Wrap -> Undo restores exact original legacy JSON without grade but advances the separate ledger R. Stale expected_revision=0 cannot replay afterward, including reopen. Delete/restore and reused numeric IDs retain high-water/tombstones/instances. A grouped gesture has one stable history mutation_id; each successful command retains its OWN immutable receipt/revisions linked to that mutation_id. Its entry keeps the first before-state, latest after-state and latest command UUID; targeted Undo/Redo must name that group and its latest committed command, never an earlier command as though only that save would be reverted. Grouping never crosses the bound instance/action/owner. A new edit after Undo starts a new group. No-op, stale/conflicting target, unsupported or corrupt grade never moves history.

CROSS-PROCESS-AB regression uses independent OS processes and TWO distinct clips in ONE project:

1. Normal exclusion: A acquires lease, edits A and keeps snapshot; B startup/edit of B fails STORE_IN_USE BEFORE Database/schema/assets. A Undo/Redo remains valid and affects A only; B raw bytes unchanged. Prove Windows packaged and Linux, not only threads/connections.
2. Handoff/stale owner: after A edits A, terminate A or use a TEST-ONLY ownership-loss hook retaining a stale client/snapshot. B acquires only after actual release, advances E, edits B and commits. Old A ticket/resumed object cannot Undo or Redo (STORE_OWNERSHIP_LOST/STALE_OWNER/HISTORY_CONFLICT), changing neither row/ledger/receipt. After B exits, a re-admitted A has EMPTY history and cannot reuse its prior snapshot. Repeat A-Redo after A-Undo, and two projects.
3. Independent fence proof: TEST-ONLY fixture connection simulates an out-of-protocol B commit with advanced S while A retains cursor. Both A-Undo and A-Redo fail HISTORY_CONFLICT BEFORE restore, despite unchanged A revision; B/JSON/tokens/receipt stay committed, stale A stack is quarantined. This injection is NOT a production lock bypass or supported multi-writer mode. Failure of either exclusion or fence tests is STOP.

## F. Admission / activation / recovery state machine

Explicit opt-in names source identity; later downgrade has SEPARATE loss acknowledgement. Resolve safe paths/filesystems/private permissions under A/B first. Recovery names are unique UTC+UUID, create-only and never automatically pruned. No original media/SRT/log/soundtrack copy. Missing/changed REFERENCED managed assets abort, not a fabricated restore guarantee.

- ADMIT: new app accepts default/configured L or C only with verified exact anchor/parent identity; arbitrary descendant/staging/recovery as writable canonical root is rejected. Old arbitrary D behavior is tested separately. Acquire permanent C lifetime lease before writable open/init. Existing partial canonical/staging/activation artifacts without a completed valid state mean BLOCKED_RECOVERY, never fallback to L. Ordinary legacy startup with no activation artifacts/opt-in remains unchanged; no canonical setup on read.
- QUIESCE: no current-app scan/export/writer, explicit restart/cutover. SOURCE guard connection holds BEGIN IMMEDIATE with NO content DML; busy after 5s aborts. Reject a source requiring recovery before opening the guard; do not repair it implicitly. A DIFFERENT read-only source connection/read transaction performs backup, not the write-reserved connection itself. No source DML/schema/journal-mode change is allowed. Source unchanged means exact logical rows/JSON/assets, not an assertion that normal SQLite sidecar/checkpoint housekeeping preserves physical main/WAL file bytes; physical snapshot SHA is taken from the completed recovery copy. Reservation prevents competing legacy DB commits across snapshot/cutover in rollback-journal AND WAL modes; both need proof. SQLite does NOT freeze source assets: old LUT deletion can unlink BEFORE attempting a catalog write. Verify copied bytes against catalog/reference metadata and before/after identities; inconsistent/missing copy aborts. A deletion after a verified independent retained copy cannot remove that copy. Old-side writes after releasing reservation are acknowledged namespace divergence, never auto-reconciled.
- SNAPSHOT: SQLite backup API into NEW recovery staging DB, not raw live DB/WAL byte copy. Copy independent app-owned objects; record hashes/lengths/formats/logical IDs and source identity. LUT catalog SHA must match. Require integrity_check=ok, empty foreign_key_check, protected row counts/exact JSON and complete referenced asset mapping. Missing/changed/unreadable/escaping object, disk full, source change, busy or validation failure aborts activation. Technical bases: [SQLite backup](https://www.sqlite.org/backup.html), [transaction semantics](https://www.sqlite.org/lang_transaction.html). This is a protocol to validate, not existing evidence.
- RECOVERY_VERIFIED: manifest contains recovery ID/source identity/seed DB SHA/object hashes+bindings/formats/opt-in acknowledgement, no secrets. Verify synthetic restore drill from precisely this mapping before first production activation. Flush and publish unique recovery directory/manifest create-only; partial bundle is never valid. Interrupted bundles remain retained for explicit recovery, not overwritten or pruned.
- FORK_PREPARED: clone the VERIFIED snapshot (not a second moving source) to C staging; copy independent owned objects into A's custom paths. Add G/format/token/project/asset metadata ONLY to fork; raw legacy JSON remains identical. Seed instances/effective revisions without grade envelopes. Validate snapshot/source unchanged and FK/integrity/mapping. Close old current-app db/history/control objects; no live retargeting or queued old-store execution ticket survives cutover.
- ACTIVE: flush fork/objects and publish versioned activation.json LAST, staged marker + same-filesystem atomic replacement. Fields: format=1, min_store_reader=1, required capability canonical-grade-store-v1, grade_schema_versions=[1], evaluator IDs legacy-v1/managed-sdr-v1, G, exact relative DB/object paths, recovery ID+manifest SHA, source/seed identity and consent IDs. Compare protocol capabilities, not a guessed application semver; unsupported required versions/evaluators fail before schema initialization. Validate stored grade envelopes read-only through the merged Foundation, preserving diagnostics/original values; no validation read saves or normalizes JSON. Validate DB grade.v1/store G agrees. Marker is NOT owner exclusion. DB/filesystem publication is not one atomic transaction: interrupted/torn/missing state blocks, no false availability promise. On next process, acquire lease, validate marker/capabilities and DB identity read-only through raw sqlite3 URI mode=ro BEFORE Database(...)/schema init, then admit E. New commands only after admission/guard matrix; no canonical grade write during partial activation.
- REOPEN: acquire lease BEFORE SQLite journal/WAL recovery. Never use immutable=1 to ignore WAL. If read-only admission cannot read/recover safely, STORE_RECOVERY_REQUIRED; explicit owned repair may use raw writable SQLite recovery only (no app schema/grade writes), verify integrity, then repeat read-only identity/capability check. Unknown reader/G mismatch/corrupt marker/grade/missing DB or object blocks, never creates an empty replacement. Seed DB SHA is historical, not compared against normally mutated current DB; active immutable object bindings validate bytes.
- RESTORE/DOWNGRADE: separate explicit consent names recovery ID, NEW empty target T and loss of post-snapshot edits. Hold source store lease (or STORE_IN_USE), verify bundle, reserve create-only destination staging; never overwrite/merge L/C/R/existing T. Materialize DB as T/orga-drone.sqlite3 and independently copy logical objects to T/luts and T/overlay-assets using retained original formats/bytes. ONLY these new downgrade copies intentionally use old selectors. Verify hashes/FK/integrity/rows and supported old-path opening; publish destination readiness LAST. Failed/partial T remains unready and originals intact; retry requires explicit new unique destination or inspected recovery action, not silent overwrite. Old edits in T diverge without syncing back; original source availability remains honest/offline when missing.

Error transitions: contention STORE_IN_USE/no initializer; unsafe identity/permissions/path/filesystem STORE_ADMISSION_FAILED; unsupported capability UNSUPPORTED_STORE; missing/invalid activation/G or interrupted publish STORE_RECOVERY_REQUIRED; bad hashes/FK/integrity BACKUP_VERIFICATION_FAILED or STORE_RECOVERY_REQUIRED; source busy/change SOURCE_BUSY/SOURCE_CHANGED; existing target/absent separate consent RESTORE_TARGET_EXISTS/CONSENT_REQUIRED; space/I/O/flush failure aborts current phase without activation/success receipt.
