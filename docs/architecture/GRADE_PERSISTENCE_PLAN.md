## Verified persistence and startup

- `config.py::Settings.db_path` currently always returns `data_dir / "orga-drone.sqlite3"`. `ORGA_DRONE_DATA_DIR` selects the directory; there is no version-aware store selector here.
- `app.py::create_app` constructs `Database(settings.db_path)` early. `Database.__init__` creates the parent and calls `_init_schema`; this executes SCHEMA and `_migrate`. A compatibility check after construction is too late to claim a read-only/minimum-reader admission gate.
- `Database.connect` owns SQLite connection/commit/rollback/close. Callers can reuse one connection in the newer transactional APIs; many old setters still open their own transactions and re-read after commit. Do not nest them inside a purported atomic grade transaction and assume a rollback will undo an earlier connection's commit.
- `studio_clips.effect_settings` already stores extensible JSON. No new column/table is demonstrated necessary for the grade envelope. Existing `app_state` can potentially store revision/activation metadata without schema changes; its key semantics and concurrency protocol require review before use.
- User media and soundtracks remain references. Application-owned LUTs are in `data_dir/luts`; imported overlay assets are in `data_dir/overlay-assets`. A database-only backup does not prove rollback preserves old looks if the newer app deletes/replaces these assets in the shared directory. Asset namespaces must be part of the fork/recovery contract. Source media, flight logs and soundtracks must not be copied into backups by this feature.
- Rescan must retain media_meta, album_items and studio_clips exactly as before. A grade read must not select a new database, normalize/save JSON, call a setter or trigger a wrapper conversion.

## Existing history: reuse and limits

`studio_history.py` already supplies a process RLock, project-keyed stacks, 50-entry session history, full clip-row snapshots and project music start. `transactional_story_edit` captures before/after inside BEGIN IMMEDIATE and publishes stacks after commit; `transactional_story_undo` has a pre-restore validation hook and publishes stacks after commit. These are the primary reusable boundaries.

Generic Story undo intentionally restores a PROJECT snapshot. A row's presence in that snapshot is not proof that the last mutation targeted that clip. `guarded_undo_values` alone is insufficient command attribution. Existing ControlService additionally compares ExternalOperation(session/project/clip/command/history revision/fingerprint), and existing two-clip tests cover that legacy integration. Reuse those checks; do not infer a new cross-target defect from the snapshot design or bypass its surrounding guard.

`redo_story` currently pops/restores the snapshot via its own connection and then updates stacks; canonical revision reassignment must occur in the SAME SQLite transaction as the restored JSON. Snapshot-restored old grade revisions would permit stale requests. Both undo and redo need a serial, reviewed extension; do not patch only the forward grade setter.

Gesture grouping currently uses a string open_group. Future canonical grouping must bind project, clip, command/gesture and mutation type, so reusing a group ID across A/B cannot coalesce distinct targets. A grade-specific undo/redo must match the top entry's recorded mutation and expected revision, never search an older entry or claim a clip was undone because its row existed in a project snapshot. Generic Story undo remains project-scoped and must refresh every affected canonical revision.

Do not create a second undo engine. Extend existing history entries with reviewed provenance and reuse its transactional snapshot machinery. A confirmed cross-target or non-atomic restore regression is a STOP condition, not a finding to fix opportunistically outside approved safety design.

## Proposed internal atomic action and revision rules (not implemented)

The Foundation remains the sole parser/pure command validator after it merges. Proposed new `studio_grade_persistence.py` owns the transactional service; proposed `studio_grade_store.py` owns store admission/backup. Existing db/history/control entry files only delegate or implement explicitly approved serial integration hooks.

A persistent action receives immutable store-generation/project/clip/command identity, expected revision and the Foundation command. The service must verify project membership and media/clip support itself, not trust UI selection or the pure validator's positive integers. Authentication/selection/lease checks remain in existing transport admission and #363. Use one lock order (existing history guard, then DB transaction); never acquire it in reverse in another entry point.

Within one BEGIN IMMEDIATE: verify activated store and current target, read raw JSON, reject corrupt/unsupported authority, compare expected revision, validate the detached proposal, allocate a NEW token, write grade and project timestamp, and prepare history/provenance/command receipt from the same connection. UPDATE must match project AND clip AND expected state; assert one changed row. On any exception rollback DB and leave history/redo/receipt/revision state unchanged. Only after commit publish preallocated in-memory history state/ack; post-commit failure must be recoverable by reading the committed command receipt, not reported as an uncommitted mutation. No-op leaves revisions/history untouched. Do not use the existing post-commit setter re-read pattern as the only success acknowledgement.

Candidate revision design for review: a monotonic database-generation allocator and per-clip durable token in existing app_state keys, updated in the same transaction. JSON grade.revision mirrors the current token when canonical. This avoids restoring old tokens during undo/redo and prevents ABA across delete/restore or wrap/undo/reopen. A subtle required decision: undoing an explicit wrapper can restore the exact legacy JSON with NO grade while a prior canonical request still exists. The durable token must survive outside that JSON; returning Foundation's legacy sentinel revision=0 as the persistent current revision would permit replay. #351/#363 must agree on an effective revision in action snapshots without changing the Foundation's raw legacy read semantics. Do not introduce the allocator/ledger without reviewing those key semantics and failure tests. Exhausted JS-safe counters fail closed; never reset/wrap.

Command identity must be bound to request digest and target generation/project/clip. Exact retry cannot repeat the mutation; a reused command ID with different target/payload must conflict. Late requests must fail STALE_REVISION rather than overwrite a newer grade, including after undo/redo/reopen. Receipt lifetime/storage and duplicate acknowledgement semantics are an explicit internal contract to finalize before code; process-only deduplication is not sufficient evidence for restart safety. No new database table is assumed or authorized here.

## Concrete backup/store proposal for PO decision

All paths below are proposals, not files created by this PR. Let L be the configured existing data directory (including an explicit ORGA_DRONE_DATA_DIR). No absolute user/library paths, secrets or private media are committed in manifests/evidence.

1. Retain `L/orga-drone.sqlite3` as the legacy store; never overwrite/rename it during activation. Proposed canonical namespace: `L/grade-store-v1/orga-drone-grade-v1.sqlite3` plus separately owned `luts/` and `overlay-assets/` beneath that namespace. The different database filename also protects default selection if an old binary receives the new namespace as its data directory: it still seeks orga-drone.sqlite3, not the canonical filename. Media paths/library roots/soundtracks remain references to their original locations.
2. Proposed recovery namespace: `L/grade-recovery-v1/<UTC timestamp>-<random UUID>/legacy.sqlite3`, retained app-owned assets and `manifest.json`. Unique names, create-only publication, no overwrite and no automatic retention pruning. Normal inherited per-user directory permissions; verify owner/access and reject an unsafe shared/network destination. File attributes/read-only flags are NOT protection from an older same-user executable. Exact Windows permission/admission behavior and supported filesystem assumptions require PO/security review and packaged evidence.
3. Capability gate proposed as `canonical-grade-store-v1`, grade schema/evaluator versions explicitly listed in the activation manifest. Do not invent a released application version number. Validate capabilities/manifest integrity/store generation BEFORE Database(...) or any schema initializer, including browser/desktop startup and direct store-opening helpers. Unknown/missing/corrupt activation data with a canonical namespace present means a recoverable blocked startup; never fall back silently to the legacy DB.
4. Require explicit opt-in and a quiescent upgrade point before the application opens its writable store; active writers/jobs or inability to establish source consistency must abort without activation. Use SQLite's backup mechanism for a consistent snapshot, not a byte-copy of a potentially active SQLite/WAL file. Do not silently detach a live app's db/history/control objects to another store. A restart/cutover is required before a pending canonical command can execute. Final locking/quiescence protocol must be reviewed and tested for rollback-journal AND WAL modes, competing writers and Windows locks before approval; this document does not claim that a marker excludes an old process.
5. Clone the same verified snapshot into the canonical namespace and retain all referenced app-managed assets separately, with SHA-256 manifests. Run SQLite integrity/foreign-key checks, compare row counts and exact protected row/JSON values, verify asset bytes/references, and perform a restore/read drill using disposable synthetic copies. Reject pre-existing ambiguous canonical grade content in a claimed legacy source. Hash manifests are integrity checks, not cryptographic protection against an adversarial same-user process. Never write media or copy them as part of the drill.
6. Stage inside the same destination filesystem; complete and verify backup and fork before atomically publishing a final `activation.json` marker. Canonical writes require that validated marker and this generation. Interruption after any phase leaves the legacy store retained and the partial destination unactivated/recoverably blocked. Directory/marker publication and SQLite transactions are not one atomic operation: an explicit state machine and crash matrix are mandatory; no grade mutation occurs before activation/cutover completes.
7. Proposed downgrade is an explicit point-in-time restore to a NEW user-selected recovery data directory, with `orga-drone.sqlite3` and verified app-owned assets. Do not overwrite the legacy store, canonical store, exports or sources. Keep the canonical store/recovery artifacts intact. The user must explicitly acknowledge that post-snapshot canonical edits are NOT represented in the old application. Do not translate new operations back into legacy sliders. External media missing at restore time remains honestly offline; backup verification cannot fabricate source availability.
8. Old app and canonical app using their own namespaces can diverge. No sync or merge of subsequent legacy-side edits is authorized. PO must accept this limitation and decide supported launch/override/downgrade behavior. The new app cannot force an unmodified old executable to recognize a manifest or prevent a human manually renaming/replacing database files. Guarantee proposal: isolation for supported, unmodified launch/configuration paths; arbitrary manual DB substitution is outside that guarantee. If the requirement instead includes arbitrary old executables/filesystem manipulations, STOP for a revised architecture rather than claim this proposal fulfills it.

PO approval must identify the exact path/capability/permissions/quiescence/publication/restore/consent policy, not merely say "add a backup". Until then first canonical write is forbidden even after #370 merges. This is the required downgrade-safety STOP, not a silent workaround.

## Planned regression matrix (all canonical implementation cases NOT_RUN)

- Read-only legacy: compare pre/post raw rows and whole DB state using a read-only connection/trace; normal malformed legacy defaults preserved. No setter/wrapper/activation invoked. Existing canonical root-member corruption handling must be reused from merged #370, including bad strings before grade.
- Save/reopen: canonical neutral + disabled opaque operation + foreign nested JSON survive exact JSON-value roundtrip; close all connections/reopen using the approved store selector. Unrelated media_meta, album_items, studio rows and assets unchanged.
- Revision/stale: simultaneous connections/processes with same expected token produce one successful mutation; losers STALE_REVISION. Delayed writes after forward edit, undo, redo, close/reopen, cut/delete/restore and wrap/undo cannot exploit a recycled token.
- Command/target: correct ID but wrong project/clip/generation/command/digest fails before mutation. Exact retries acknowledge once, collisions conflict. Session selection changes cannot redirect an already validated target.
- Atomicity: inject at validation, allocator, row update, timestamp update, history capture, receipt preparation, commit and acknowledgement. Compare raw JSON, durable tokens, command receipts, updated_at and undo/redo stacks before/after; no partial transaction. Ambiguous post-commit acknowledgement resolves from receipt, never replays the write.
- Two-clip history: mutate A then B, attempt A-targeted undo of B's command and vice versa; reject without touching either clip/history. Correct B undo/redo affects B only, with fresh token. Same gesture ID on A/B must not coalesce. Repeat with two projects and project switching. Generic project Story undo restores the intended snapshot and refreshes all affected tokens.
- Failed history: inject restore and commit failures in BOTH undo and redo; stacks/token/JSON remain coherent. Restart drops session undo stacks as today but preserves durable current state, receipt/revision safety and exact saved JSON.
- Guards: parameterize every inventoried legacy/direct SQL/structural writer against canonical, unknown evaluator, disabled unknown data and damaged JSON. Either preserve the entire grade with correctly refreshed tokens or reject before any write. Read/export/rescan cannot silently migrate or recover corrupt grade to legacy.
- Backup/restore: valid SQLite and assets, missing/modified LUT/overlay, disk full, denied permissions, source change, active old writer, rollback journal/WAL, interrupted copy/validation/activation, corrupt manifest, wrong minimum reader, existing destination and unavailable media. Restored synthetic store must match snapshot and open through a supported old-path test; no original user store is used for testing.
- Concurrency/lifetime: history lock versus DB lock ordering, bounded SQLite busy handling, process restart, stale in-memory receipts, wrong generation and revision exhaustion. No irreversible filesystem publication before all required checks.
- Windows/packaged: unlike a pure model unit, this feature changes store startup and recovery. Planned real Windows EXE/WebView2 tests must cover default directory and ORGA_DRONE_DATA_DIR, old/new namespace selection, restart, denied access/locked files, interrupted activation and offline restore. Claiming blanket packaged NOT_APPLICABLE would be incorrect. No release/binary publication is authorized.
